## Спецификация сервиса структурированного хранилища

### 1. Общие положения
Сервис предоставляет универсальный интерфейс для долговременного хранения, поиска и организации произвольных JSON-объектов. Данные сохраняются в СУБД PostgreSQL. Каждый объект идентифицируется уникальным текстовым ключом и состоит из двух логических частей:
- **метаинформация** (описание, теги, положение в иерархии);
- **содержимое (контент)** — JSON-объект произвольной структуры и размера, сохраняемый в формате JSONB.

Хранение метаданных и контента физически разделено, однако программный интерфейс скрывает этот факт и представляет сущность как единый объект. Контент загружается и сохраняется через отдельные операции, что позволяет оптимизировать передачу данных и избегать избыточной пересылки полезной нагрузки при работе с метаинформацией.

Допускается существование мета-записей без связанного контента — так называемые виртуальные узлы, которые могут использоваться для построения иерархий, каталогов или групп.

### 2. Модель данных
Реляционная схема включает две таблицы, связанные общим первичным ключом `key`.

#### 2.1. Таблица `storage.data` — содержимое объектов
| Поле   | Тип        | Ограничения   | Описание |
|--------|------------|---------------|----------|
| `key`  | `TEXT`     | `PRIMARY KEY` | Уникальный идентификатор объекта |
| `value`| `JSONB`    | `NOT NULL`    | Произвольный JSON-объект |

Строка в этой таблице существует только для тех объектов, у которых загружен контент. Временные метки не хранятся.

#### 2.2. Таблица `storage.meta` — метаинформация объектов
| Поле          | Тип        | Ограничения                                   | Описание |
|---------------|------------|-----------------------------------------------|----------|
| `key`         | `TEXT`     | `PRIMARY KEY`                                 | Уникальный идентификатор (общий с `data.key`) |
| `description` | `TEXT`     |                                               | Произвольное текстовое описание |
| `tags`        | `TEXT[]`   | `NOT NULL DEFAULT '{}'`                       | Массив строковых тегов (свободный формат) |
| `parent_id`   | `TEXT`     | `REFERENCES storage.meta(key) ON DELETE ...`* | Ключ родительского узла в иерархии (`NULL` для корневых элементов) |
| `created_at`  | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()`                    | Дата и время создания мета-записи |
| `updated_at`  | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()`                    | Дата и время последнего изменения мета-записи |

*Стратегия поведения при удалении родительского узла определяется конфигурацией сервиса (по умолчанию `ON DELETE SET NULL`, что сохраняет дочерние узлы, но делает их корневыми).

**Связь между таблицами**:
- Если в `data` существует запись с ключом `K`, то в `meta` обязательно присутствует запись с тем же ключом (поддерживается логикой приложения).
- Допускается наличие записи в `meta` без соответствующей записи в `data` — это означает виртуальный узел без контента.
- Обратная ситуация (запись в `data` без записи в `meta`) недопустима.

Для ускорения полнотекстового поиска по описанию и поиска по тегам предполагается создание индексов: GIN-индекс на поле `tags` и, при необходимости, индекс для текстового поиска (`pg_trgm` или полнотекстовый) на поле `description`.

### 3. Программный интерфейс (API)
Взаимодействие с сервисом осуществляется через сетевой протокол (например, HTTP REST или gRPC). В качестве формата обмена данными используется JSON. Далее конечные точки описаны в стиле REST для наглядности, однако фактический протокол может отличаться; семантика операций остаётся неизменной.

Все операции оперируют единым идентификатором `key`. Идентификатор задаётся клиентом при создании объекта и представляет собой произвольную непустую строку. Рекомендуется использовать иерархические ключи (например, `projects/123/tasks/456`) для естественной организации пространства имён.

#### 3.1. Атомарные операции над объектом (скрывают разделение мета/контент)

**Создание или полное обновление объекта**
```
PUT /objects/{key}
```
Тело запроса — JSON-объект со следующими необязательными полями:
- `content` — JSON (контент объекта);
- `description` — строка;
- `tags` — массив строк;
- `parent_id` — строка (ключ существующего родительского узла или `null`).

Поведение:
- Если объект с ключом `key` не существует, создаётся новая мета-запись. При наличии поля `content` дополнительно создаётся запись в `data`.
- Если объект уже существует, мета-поля (`description`, `tags`, `parent_id`) обновляются переданными значениями (при отсутствии поля в запросе сохраняется предыдущее значение). Поле `content`, если передано, полностью замещает существующий контент; если не передано — контент остаётся без изменений.
- Сервер проверяет, что `parent_id` (если указан) не приводит к циклу и ссылается на существующий узел. Валидация цикла включает проверку, что `parent_id != key` и что среди предков указываемого родителя отсутствует текущий ключ.

Ответ: JSON-представление мета-записи (без контента) с флагом `has_content: true/false` и кодом `200` (обновление) или `201` (создание).

**Частичное обновление метаданных**
```
PATCH /objects/{key}
```
Тело запроса — JSON, содержащий один или несколько атрибутов: `description`, `tags`, `parent_id`. Допустимо комбинировать любые поля.

Поведение: изменяет только указанные поля мета-записи. Контент не затрагивается. Если объект не существует, возвращается ошибка `404`.

**Получение информации об объекте (без контента)**
```
GET /objects/{key}
```
Возвращает мета-запись: `key`, `description`, `tags`, `parent_id`, `created_at`, `updated_at`, `has_content` (логическое поле, вычисляемое по наличию записи в `data`). Контент в ответ не включается. Если ключ не найден — `404`.

**Удаление объекта**
```
DELETE /objects/{key}
```
Удаляет мета-запись и, при наличии, связанный контент. Дочерние узлы, у которых `parent_id` равен удаляемому ключу, обрабатываются согласно настроенной стратегии:
- `SET NULL` (по умолчанию) — дочерние узлы становятся корневыми (`parent_id = NULL`).
- `CASCADE` — все дочерние узлы также рекурсивно удаляются.
- `RESTRICT` — удаление запрещено, если есть дочерние узлы (возвращается ошибка).

При любом варианте контент (если был) удаляется безвозвратно.

#### 3.2. Поиск объектов
```
GET /objects
```
Поддерживает фильтрацию и пагинацию через параметры запроса:
- `tags` — список тегов через запятую (например, `tags=важное,черновик`). Поведение уточняется параметром `tag_mode`:
  - `all` — объект должен содержать все указанные теги (пересечение);
  - `any` — объект должен содержать хотя бы один из указанных тегов (объединение, используется по умолчанию).
- `description_contains` — строка для поиска по описанию (поиск по подстроке или полнотекстовый, в зависимости от конфигурации индекса).
- `has_content` — булево значение (`true` или `false`). Фильтрует объекты по наличию/отсутствию контента. Если параметр опущен, возвращаются объекты с любым состоянием.
- `parent_id` — точное совпадение родительского ключа. Специальное значение `null` выбирает только корневые узлы (у которых `parent_id IS NULL`).
- `key_prefix` — строковый префикс; возвращаются объекты, у которых ключ начинается с заданной подстроки.
- `limit` и `offset` — для постраничной выдачи (значения по умолчанию: `limit=50`, `offset=0`).

Ответ — JSON-массив мета-объектов (без контента), каждому элементу соответствует описанная выше структура с флагом `has_content`. Порядок сортировки по умолчанию — по `created_at` по убыванию (новые первые). Допускается дополнительный параметр `sort` для изменения критерия сортировки (детали могут быть уточнены).

#### 3.3. Операции с иерархией
**Получение потомков**
```
GET /objects/{key}/children
```
Возвращает плоский список всех прямых и непрямых потомков узла `key` (рекурсивный обход в глубину или в ширину, порядок не гарантируется). Включён флаг `recursive` (по умолчанию `true`), при значении `false` возвращаются только непосредственные дочерние узлы.

**Получение предков**
```
GET /objects/{key}/ancestors`
```
Возвращает массив предков от корня до `key` (в порядке от корня к `key` или наоборот — уточняется параметром). Если узел корневой, возвращается пустой массив.

#### 3.4. Операции с контентом (оптимизированные)
Эти эндпоинты предназначены для прямой работы с полезной нагрузкой без передачи метаданных.

**Загрузка контента**
```
GET /objects/{key}/content
```
Возвращает содержимое в виде JSON-объекта, хранящегося в `data.value`. Если объект существует, но контент отсутствует, возвращается `404`. Заголовки ответа должны поддерживать потоковую передачу (например, `Transfer-Encoding: chunked`) для эффективной работы с большими объектами.

**Сохранение/замена контента**
```
PUT /objects/{key}/content
```
Тело запроса — произвольный JSON. Если мета-запись для данного ключа не существует, она автоматически создаётся с пустыми полями (`description=null`, `tags=[]`, `parent_id=null`), после чего сохраняется контент. Если мета-запись уже есть, контент создаётся или замещается. Таким образом, этот вызов гарантирует, что после выполнения объект будет иметь контент.

**Удаление контента**
```
DELETE /objects/{key}/content
```
Удаляет запись из `data`, оставляя мета-запись нетронутой. Объект превращается в виртуальный узел. Если контент отсутствовал, операция идемпотентна и возвращает успех (код `204` или `200`).

### 4. Требования к реализации и поведению
- **Язык и технологии**: серверная часть реализуется на C++20 с использованием библиотек POCO, Boost и Soci. Взаимодействие с PostgreSQL осуществляется через Soci.
- **Целостность данных**:
  - Все изменения в рамках одного запроса к API должны быть атомарны: либо фиксируются целиком, либо не вносят изменений.
  - При создании контента через `PUT /objects/{key}/content` мета-запись создаётся в той же транзакции, что и вставка в `data`.
  - Удаление объекта (`DELETE /objects/{key}`) удаляет и мета, и контент в одной транзакции.
- **Валидация**:
  - Входящий JSON для контента проверяется на синтаксическую корректность. Сервер должен возвращать понятную ошибку при нарушении формата.
  - Ключ `key` должен быть непустой строкой длиной до 2048 символов, допускаются символы Unicode. Запрещены управляющие символы.
  - `parent_id` проверяется на существование и отсутствие циклов.
- **Производительность**:
  - Время ответа на чтение контента объёмом до 1 МБ не должно превышать 100 мс при типовой нагрузке (исключая сетевые задержки).
  - Для больших JSON-объектов (вплоть до 1 ГБ) сервер должен обеспечивать потоковое чтение/запись из базы без полной загрузки в оперативную память. Драйвер Soci и POCO должны быть сконфигурированы соответствующим образом.
- **Идемпотентность**: операции `PUT` (как над объектом целиком, так и над контентом) идемпотентны. Повторный вызов с теми же параметрами не изменяет состояние и не вызывает ошибок.
- **Логирование и мониторинг**: все критические операции (создание, изменение, удаление) должны протоколироваться с указанием времени, инициатора (если доступен) и сути изменения. Формат и уровень логирования определяются на этапе проектирования архитектуры.
- **Безопасность**: предполагается возможность добавления аутентификации и авторизации; на уровне спецификации API предусматривается, что заголовки или метаданные запроса могут содержать учётные данные. Конкретный механизм определяется позже.

### 5. Примеры использования
**Создание нового документа с контентом**
```http
PUT /objects/docs/report-2025
Content-Type: application/json

{
  "content": {"title": "Годовой отчёт", "sections": ["Введение", "Анализ", "Заключение"]},
  "description": "Финансовый отчёт за 2025 год",
  "tags": ["финансы", "отчёт", "2025"],
  "parent_id": null
}
```
Ответ: `201 Created`; мета-объект с `has_content: true`.

**Создание папки без контента**
```http
PUT /objects/docs/archive
Content-Type: application/json

{
  "description": "Архив документов",
  "tags": ["архив"]
}
```
Создаётся только мета-запись, `has_content: false`.

**Добавление документа в папку**
```http
PATCH /objects/docs/report-2025
Content-Type: application/json

{
  "parent_id": "docs/archive"
}
```
Теперь документ стал дочерним для узла `docs/archive`.

**Поиск всех отчётов за 2025 год с тегом "финансы"**
```http
GET /objects?tags=финансы,2025&tag_mode=all&has_content=true
```
Возвращает массив мета-объектов, удовлетворяющих условию.

**Загрузка только контента**
```http
GET /objects/docs/report-2025/content
```
Ответ: `{"title": "Годовой отчёт", "sections": [...]}`.

**Удаление контента с сохранением метаинформации**
```http
DELETE /objects/docs/report-2025/content
```
Объект остаётся в иерархии с `has_content: false`.
